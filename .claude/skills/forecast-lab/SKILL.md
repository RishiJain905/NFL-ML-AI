# Forecast lab (availability and role, outcome curves)

Spec: `documentation/forecast-lab/README.md` (+ phase files FL00-FL02, the mockups in `mockup/`). Plain-language guide: `documentation/guides/forecast-lab.md` (§3 availability, §4 curves, §6 the refresh, §8 the tabs, §9 a recipe for reading the files). Model cards: `documentation/model_cards/availability-and-role.md`, `outcome-curves.md`. W&B: guide §6.15. Decision: D158 (D107 is the no-touch rule it keeps; D100 the "read whole, don't hold" rule; D157 the Tailscale read-only rule it respects).

## 1. The rules that are easy to break

- **No-touch (D107).** New code lives in `src/nflengine/forecastlab/` and the app. It reads curated data and the player model's published files and **never writes** to them, to any production model, feature, setting, artifact or alias, the digest, the weekly graph or `weekly.py`. Shared files change only by adding (the `forecastlab` CLI group, the `forecastlab:` settings block, the app's kind / gate / readers / routes). `tests/test_production_untouched.py` checks it; every close runs the production-unchanged check.
- **Never read the game-day inactive list.** `rosters_weekly.status == 'INA'` is folded into `ACT` everywhere (`availability.ROSTER_CAT`), in every week and view, and a test pins that replacing every `INA` changes no row. Don't add a feature that sees it, however good it looks (the leak test: inactive players who weren't Out or Doubtful got an average 58-60% chance; a model that saw the list would give ~0).
- **The Tuesday view never reads week W's report or roster row.** One exception: **week 1**, where week 1's own roster row decides *membership* only. The Saturday view reads the final report and **one folded roster value** (`ACT` incl. practice squad and `INA`; `RES`; `OFF`; null when the team has no rows yet). `injuries.date_modified` is null for 2025-2026, so a report can't be time-scoped.
- **History is strictly before the week.** Availability: every feature uses games before W; walk-forward refits on every earlier week; calibration (Platt layer, range shifts) from the run's own earlier predictions (the last `calib_seasons`, never the block itself). Curves: a week's analogs are rows before (season, week); `load_history(before=)`. A projection with no result (he didn't play) is not history. A test scrambles actuals from a week on and checks nothing at or before it moves: keep it passing.
- **Never re-make a row after its game kicks off** (`run_predict`'s `now`): rows the file already holds for a started game stay exactly as they are (`games_kept_after_kickoff` / `games_kept`); a started game with none is made and listed in `games_after_kickoff` (the tabs mark it). The update asks again right before each step (`clock=`), because a plan can be minutes old.
- **Read curated and published files whole and don't hold them** (`schema.read_parquet`, `memory_map=False`; D100): a weekly run's curate step replaces files and a held handle fails on Windows. Never `scan_parquet` or `pl.read_parquet` a curated file; don't start DuckDB on one.
- **The windows are pre-registered.** Availability: train from 2014, tune 2017-2018, report 2019-2025 (walk-forward predictions from 2015). Curves: history from 2017, tune 2019-2020, report 2021-2025. Choose settings on the tuning window only; touch the reported window once the settings are fixed; write the ship rule down (a timestamped note, then the decisions log) **before** the reported run; keep both run ids when a run is repeated. A miss doesn't ship and goes to Rishi.
- **Pooled and by-season, same rows.** The model and every baseline are scored on exactly the same rows (`availability.cohort`, the curves' shared grid). Shares only for players who played. Say "a gain under noise" when it is one: passing yards' curve is 0.10% better than the bell curve (4 of 5 seasons) and ships by the letter of the rule.
- **Don't oversell.** A curve is "if he plays" (built only from played games) and doesn't make ranges tighter; the chance he plays is availability's; the play baseline doesn't know playing-time history, so part of the gain is knowing who's a regular; the Saturday backtest uses the week's final roster row as a stand-in (about 0.4% of rows carry later information). No betting vocabulary in docs, tabs or code comments ("the chance of more than 49.5 yards" is fine).
- **The digest never reads these files.** A threshold chance is a property of the projection, shown in the control room only.
- **W&B:** only through `tracking.init_run` (group `forecast-lab`, smoke `forecast-lab-smoke`). **Agent processes can't use the W&B API**, so charts can't be viewed from an agent: list keys from the code that logs them, and say so. Never put a key whose name contains `token`, `secret`, `password`, `api_key` in a config (the refusal is in `tracking`). Deleting runs needs Rishi.
- **Never put `key`, `token`, `secret`, `password` or `auth` anywhere in a JSON field's name** in an app answer: the leak scan masks its value. `target_key` failed the scan too (it contains "key"), so the Outcomes answers call the field `stat`; the parquet column stays `target_key` and the query parameter `target`. A new W&B run or artifact goes in `documentation/guides/weights-and-biases.md` in the same commit.

## 3. The two models in a paragraph each

- **Availability:** the as-of list (QB RB WR TE DL LB CB S with a snap on his side in one of the team's last 3 games, latest appearance for the team, latest roster row not elsewhere); per view LightGBM binary + a Platt layer (the chance he plays), three quantile LightGBM models for the snap share (**the 90th percentile is fit reflected**: 13% of shares are exactly 1.0 and the plain 0.9 model never moved; range ends then shifted by the last 2 seasons' misses), L1 regressions for target and carry share, the teammates' risk `vac_*` (training: who actually sat; forecast: 1 - `p_play`), and `inherit_table` (shares with a player in vs out). Weekly refits in the backtest and in the live predict. `at_risk` = chance < 0.85 or a Questionable / Doubtful / Out report. Baselines: the historical play rate by status / practice line / roster status and position group (no playing-time history), the last-2-games snap mean, the rolling-4 share.
- **Curves:** a curve is built **at run time** from the player model's walk-forward history, so the model *is* its settings (`params.json`). Amounts: K nearest analogs on P50 (or P50 and width), z = (actual - P50) / max(P90 - P10, 5), outcomes `round(P50 + z w)`; `analog_zero` keeps an exact 0 as an atom, a negative as itself, a positive never below 1. Counts: negative binomial at the mean with its spread by moments on the analogs (`nb_cal` also scales the mean, clipped 0.25-4). Fewer than 100 analogs -> the bell curve. Baselines: the bell curve (normal through P10 / P90; Poisson for counts) and the player's own last 16 results (at least 6). Scores: CRPS, the Brier of "more than each standard mark", the band said vs happened, PIT error, and the "1 or more yards" Brier (a diagnostic, not in the rule).

## 4. The ship rules (as coded; don't edit after a reported run)

- **Availability (`verdicts`):** per output and view: model beats the baseline pooled and in at least 6 of 7 seasons (`wins_needed`); `play`: decile calibration error <= 0.02; `snap`: the 80% range covers 72-88% pooled.
- **Curves (`ship_verdict`):** per stat: CRPS below the bell curve's pooled and in at least `ceil(0.8 x seasons)` of the seasons (4 of 5); CRPS below the own-history baseline's; the mean marks-Brier below the bell curve's; the band's said-vs-happened gap <= 2 points. `analog_zero` replaced `analog` for the amount stats by its own pre-registered rule (CRPS no worse by more than 0.1% **and** a lower "1 or more" Brier, on 2019-2020 only).
- **Promotion** is `backtest --promote`, only from the canonical reported run (not tune, smoke or overrides). Curves: a run of only some stats is merged into the previous pointer (`sources` / `wandb_runs` say which stat comes from which version / run).

## 5. Run and test

```bash
uv run pytest -q tests/forecastlab                 # 7 files: fl_avail_* (features, model, runs), fl_curves_* (core, runs), fl_update_* (plan, run)
uv run pytest -q tests/forecastlab -k fl_avail     # the availability model (a synthetic league: fl_avail_fixtures.py)
uv run pytest -q tests/forecastlab -k fl_curves    # the curves (the atom equals the zero share; the cdf is monotone and ends at 1; equal to `analog` where nothing is zero; leakage by scrambling)
uv run pytest -q tests/app -k forecastlab          # the reader, the contract (JSON vs TypeScript), the gate, the kind, the follow-up
npm --prefix web test -- ForecastLab Outcomes      # the tabs and the Update card (Vitest)
uv run pytest -q tests/test_production_untouched.py
uv run nfl forecastlab update --auto --dry-run     # read-only: what's due and why
```

- **Never run `nfl forecastlab update / predict / grade / backtest` from a probe or while a weekly run is going**: they write files, log W&B runs and (update) hold the weekly lock. A real backtest of availability takes ~26 minutes (weekly refits); curves ~27 s (reported) and ~82 s (tuning).
- **Real-data checks that need no writes:** read a week's files with `schema.read_parquet` (the guide's §9 recipe), print Polars tables with `PYTHONIOENCODING=utf-8`; the saved backtests' `summary.json` hold every pooled and by-season number the cards quote.
- **Tests worth keeping when you change a rule:** an independent hand-worked case for each part (the universe, the folded roster value, the Platt layer, the reflected top end, `inherit_table`'s in / out, a curve for a three-row history, the zero atom), the future-invariance test, the plan case by case (`plan_update` for every skip and due reason), the CLI exit codes, the follow-up (starts once, never loops, never from a GET, never in rehearsal mode, refused over Tailscale), and the reader's blanking of an output that didn't ship.

## 6. Quirks found while building it (2026-11-14)

- **A Tuesday view can be made late.** The first real update was run on Saturday: the "Tuesday" view reads only what a Tuesday run could, but Thursday's game had kicked off, so its rows are marked `games_after_kickoff` (and the curves have no row for it: the player model's projection file had no Thursday game by then). The tabs say "made after kickoff".
- **`played` is filled at predict time** for a game whose snap counts already exist (`build_rows` adds labels), so the tab's `graded` is true for a Thursday game before any grade run; the scoreboard (and "How it did") needs `nfl forecastlab grade`.
- **Week 1 has no last-season roster to lean on:** week 1's own roster row decides membership (last season's roster kept every departed player: 49.5% played, vs 78.1% in other weeks).
- **Practice-squad players are left off the might-sit list** (`roster_status == 'DEV'`: no role to lose) and the list has a role floor of 30% of snaps (without it ~300 fringe players and healthy scratches a week). `INHERIT_MIN` hides tiny gains; a teammate who is himself out (Out, Doubtful or on a reserve list) inherits nothing; a backup quarterback's chance is low only while the starter plays.
- **Teammates' shares don't add up** (each is its own forecast): "who inherits" is learned, not a depth chart (Minnesota's QBs: Brosmer 25% -> 70% if Murray sits, Wentz 94% -> 100%).
- **The tuning window can't tell "all earlier seasons" from "the last 4" for curves** (history from 2017, tuning 2019-2020): every candidate gave identical numbers. Revisit at the pre-season retune.
- **The first amount curves smeared the zero** (an analog with 0 yards but a different P50 landed on 1 or -1): `analog_zero`. Re-scoring the first method on the same rows reproduces its CRPS to 15 digits, so keep that check when touching `_amount_cdf`.
- **The stored `cdf` list stops at the first value that reaches 1.0**; readers treat everything after as 1. `grid_lo` is the stat's floor (-15 for yardage, 0 for counts).
- **W&B `line_series` makes its own table** under `<name>_table` (LD03's lesson): name explicit tables `*_rows` / `*_bins`.
- **The promote step reads a card file for the artifact description** (`model_cards/availability.md` for availability, `forecastlab-curves.md` for curves). The cards are named `availability-and-role.md` and `outcome-curves.md`, so a promotion copies no card until the code or the names are reconciled (the artifacts' descriptions fall back to the version string).
- **A `KeyError` text** (`KeyError: x`) is masked by the secret scrubber as a `key: value` pair, so `update._err` words it "LookupError: missing 'x'".
- **Case-insensitive Windows names:** `ForecastLabUpdate.tsx` and a `forecastLabUpdate.ts` would clash: the run model is `forecastLabRunModel.ts`.
